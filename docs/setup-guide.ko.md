## SQLite 경합과 정기 스냅샷 실패

메타데이터 연결에는 WAL 모드와 1,000ms의 `busy_timeout`을 적용합니다. 스냅샷 메타데이터 저장 중 SQLite `BUSY`/`LOCKED` 오류가 발생하면 총 5회까지 시도하며, 재시도 사이에 100·200·400·800ms를 기다립니다. 실패한 트랜잭션을 롤백한 뒤 새 트랜잭션으로 재시도합니다. WAL과 타임아웃만으로 모든 경합이 해결되지는 않으므로 재시도를 함께 사용합니다. 다른 DB 오류는 재시도하지 않습니다. 재시도는 스냅샷 메타데이터 저장에만 적용되며, 스냅샷 삭제나 데이터소스 설정 저장에는 `busy_timeout`만 적용됩니다.

WAL 모드에서는 `snaplake.db` 옆에 `snaplake.db-wal`, `snaplake.db-shm` 파일이 생깁니다. 데이터 디렉터리를 파일 단위로 백업할 때는 Snaplake를 멈춘 뒤 세 파일을 함께 복사하세요.

재시도는 같은 스냅샷 ID를 사용하며 원본 DB 덤프나 스토리지 업로드를 반복하지 않습니다. 최초 저장을 재시도하는 동안에도 같은 애플리케이션 인스턴스에서 해당 데이터소스의 중복 실행을 차단합니다. 메타데이터 DB 하나당 Snaplake 인스턴스 하나를 실행해야 합니다. 여러 인스턴스 사이의 중복 실행까지 조정하지는 않습니다. 원본 DB 조회와 스토리지 I/O는 메타데이터 쓰기 트랜잭션 밖에서 실행합니다.

최초 메타데이터 저장이나 스냅샷 준비 단계에서 실패하면 같은 ID로 `FAILED` 기록을 저장하며 동일한 제한 횟수로 재시도합니다. 덤프가 끝난 뒤 `COMPLETED`나 `FAILED` 최종 상태 저장이 실패해도, DB에 `RUNNING`이 남지 않도록 그 최종 상태를 한 번 더 같은 정책으로 저장합니다. 이때 다시 저장에 성공하더라도 해당 실행은 실패로 보고됩니다. 잠금이 지속되면 이 실패 기록도 저장하지 못할 수 있습니다. 로그 모니터링에서 `event=scheduled_snapshot_failed`를 알림 조건으로 설정하세요. 데이터소스 ID와 확인 가능한 경우 스냅샷 ID를 포함합니다. `event=snapshot_failure_persistence_failed`는 실패 기록도 저장하지 못했다는 뜻이므로 스냅샷 목록에 해당 실행이 표시되지 않을 수 있습니다. 실패 결과를 정기 스냅샷 완료로 기록하지 않습니다. 같은 데이터소스의 스냅샷이 이미 실행 중이어서 정기 실행을 건너뛴 경우에는 오류가 아니라 `event=scheduled_snapshot_skipped` 경고로 남습니다.

재시도 횟수를 소진하면 해당 실행은 종료되고 다음 cron 실행 예약은 유지됩니다. DB 잠금 원인을 확인한 뒤 다음 예약 전에 백업이 필요하면 수동으로 스냅샷을 실행하세요. 서버 재시작 후 누락된 cron 실행을 자동으로 재생하지는 않습니다.
